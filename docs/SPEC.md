# 障害対応机上演習Skill システム仕様

この文書は、障害対応机上演習Skillで実現したい挙動を整理するための上位仕様です。実際に AI へ読ませる統合 Skill 本体は、この内容をもとに `.ai/skills/00-run-exercise/SKILL.md` に書き出します。演習実行時には人間が個別の skill を直接叩かなくてよいように、統合 skill ファイルを別に用意し、統合 skill がステップ別の skill または agent ファイルを直接参照します。

利用者向けの概要・使い方・参加者コマンドは [README](../README.md) を参照してください。

## 背景
効果的な障害対応机上演習では、わからないことが多い中で原因を切り分け、いかに効果的に対応手順を模索するかが重要になります。この能力を評価するためにはゲームマスターによる状況設定と質疑による段階的な情報開示が必要です。このスキルはAIにこのゲームマスターの役割を担わせます。

## Skill構成
演習実行時の人間向け入口は統合 skill ファイルだけにします。統合 skill は演習全体のオーケストレーターとして振る舞い、シナリオ選定、タイムライン生成、想定質問生成、想定回答生成、情報開示判定、タイムライン更新、ポストモーテム生成などのステップ別 skill または agent を順番に呼び出します。

ステップ別 skill または agent は、1つ1つのAIステップを個別にデバッグできる単位にします。各単位は入力、中間出力、最終出力を明確にし、前段の出力ファイルを固定入力として任意のステップだけ再実行できるようにします。

統合 skill はステップ別 skill または agent のファイルを直接参照し、順序制御、入出力ファイルの受け渡し、デバッグ再実行、演習済みシナリオIDの除外を管理します。

人間とのやりとりはすべて日本語で行います。質問、回答、能動通知、ポストモーテムなど、人間に表示される IPC の `text` は日本語にします。

skill と agent は次の基準で分けます。順序制御、IPCゲート、ファイル受け渡し、ループ判定のような決定的処理は skill にします。タイムライン作成、想定質問・回答生成、開示情報レビュー、質問・行動解釈、ポストモーテム作成のように広い context を使う生成・評価処理は agent にします。

## 実行時プロセス構成
Claude Code や Codex などのエージェントの思考過程や内部状態が対応者に見えると意図しない情報開示になりうるため、人間との会話用プロセスとゲームマスター用プロセスを分離します。

Coding Agent を起動し、統合 skill を起動すると、Coding Agent はまずビルド済みの会話用プロセス用バイナリを自動で用意し（`scripts/install-ttx.sh`。Go 環境は不要で、GitHub Release から OS/arch に合うバイナリを取得して PATH 上へ配置する）、別窓での起動を操作者へ指示します。会話用プロセスは単一バイナリ `ttx-human` として配布します。
会話用プロセスと Coding Agent は JSONL on Unix Domain Socket を IPC として通信します。
各接続は1回の req/resp（送信1件または受信1件）で完結し、会話用プロセスは接続が閉じても終了せず、未回収の参加者入力を貯めて次の接続を待ちます。Coding Agent 側の送受信は専用 CLI `ttx-ai-send` / `ttx-ai-recv` を使います。socket パスは省略時に既定パスを 3 ツールで共有し、`TTX_SOCKET` か `--socket` で上書きできます。
Coding Agent は人間へ直接質問してはいけません。質問の受付、回答、能動通知、ポストモーテムの開示は必ず IPC 経由で会話用プロセスへ渡します。

演習開始時は、まず操作者への確認（バイナリの自動用意、別窓での会話用プロセス起動と「起動したか（Y/N）」の確認、準備モードの選択）を画面が見えるうちに済ませます。会話用プロセスは別窓で起動してもらい、`ttx-ai-recv --no-wait` の終了コードで起動を裏取りできます。その後、演習ファイルを読む前に、まず「ゲームマスター側（Claude Code / Cursor）の思考過程や内部情報が映る画面を参加者から隠す必要がある」ことを提示し、理解したか（Y/N）を確認します。この理解確認はまだ隠し情報を出していない時点で行うため画面を見ていても安全で、`Y` を受け取るまで先へは進みません。`Y` の後に「10秒以内に、参加者からゲームマスター側の画面が見えないように隠してください」と案内し、短いタイマーで待ってから進みます（画面を隠せたかの完了確認は求めません。完了確認を求めると操作者が画面を見続けてしまうため、隠す動作はタイマー方式にします）。画面を隠した後は操作者へ選択肢を提示せず、判断が必要な場合は GM（Coding Agent）が自動で選び、思考過程や入力ファイルの読み込み内容が対応者に見えないようにします。

Coding Agent が人間に何かを開示したい場合は、`ttx-ai-send` で Unix Domain Socket へ送ります。会話プロセスは即時に人間に提示します。
会話プロセスは常に人間がテキストを入力可能です。入力は会話プロセス内のキューに貯められ、Coding Agent の受信要求（`ttx-ai-recv`）に応じて1件ずつ渡されます。会話の最後のアクティビティから一定時間（会話用プロセスの `--recv-timeout`、既定30分）参加者入力が無いと、待機中の受信要求はタイムアウト応答を返して打ち切られ、Coding Agent は `/abort` 相当（ポストモーテムなし）で終了します。これは、ホスト側のツールタイムアウトで受信要求を再実行し続けることによるトークン浪費を、総アイドル時間で上限化するためです（締切は最後のアクティビティ基準で測るため、再実行しても合算されます）。

### Coding Agent → 会話プロセスのメッセージ
```json
{"type":"notification","text":"PagerDutyで注文APIの5xx増加アラートが発火しました。"}
```

### 会話プロセス → Coding Agent のメッセージ
```json
{"type":"input","text":"直近のリリースはありますか？"}
```

詳細な IPC 仕様は `.ai/shared/references/ipc-protocol.md` を参照します。

参加者が使えるコマンド（`/help`・`/giveup` など）は [README](../README.md) を参照してください。

## 入力
以下を入力にAIをゲームマスターとして振る舞わせます。

| 入力 | 説明 |
| --- | --- |
| シナリオ一覧 TSV | `SCENARIO.tsv`。ゲームマスターはここから発生を仮定するシナリオを選び、状況設定します。別セッションで `./ref` 配下の仕様・設計文書を参照して肉付けします。 |
| シナリオ一覧 TSV（一覧提示用） | `SCENARIO-LIST.tsv`。各シナリオのID・初動対応部署・最初の開示可能イベントの要約を、シナリオを選びやすいよう一覧化したものです。`90-build-scenario-list` agent で事前生成し、`01b-list-scenarios` skill が表示します（所属部署キーワードで初動対応部署を絞り込んだおすすめ候補も出せます）。表示用3列（ID・初動対応部署・最初の開示可能イベント）は開示可能情報のみ（初動対応部署のみで、原因のネタバレになる概要は含めない）なので参加者へ提示しても構いません。個別訓練の推薦用に GM 内部列 `受動対応部署` も持ちますが、これは参加者へ表示しません（後続関与部署は規模・原因のヒントになるため）。 |
| 指定シナリオID | 任意入力。操作者が演習するシナリオを明示指定する場合の `SCENARIO.tsv` の ID です（おすすめ選択で候補から選んだIDもこれに含む）。指定された場合、AIは無作為選定せずそのシナリオを採用します。指定されない場合は、対応者の所属部署によるおすすめ選択を案内し、所属部署を決められないときに限り無作為に選定します（フォールバック）。 |
| 観測情報一覧 TSV | CSによるSNSの監視や PagerDuty、Datadog などの計測指標一覧です。この計測指標は机上演習中の質疑で開示していい情報です。別セッションで `./ops` 配下の障害対応手順書・監視手順・Runbook から洗い出します。 |
| 仕様・設計文書 | `./ref`。対応者からの質問に答えるために参照してよい仕様・設計文書です。 |
| 障害対応手順書 | `./ops`。対応者からの質問に答えるために参照してよい障害対応手順書・監視手順・Runbookです。 |
| 演習済みシナリオID一覧 | 任意入力。過去に演習済みの `SCENARIO.tsv` の ID 一覧です。指定された場合、AIは該当IDを除外して未演習シナリオだけをランダム順に実施します。指定されない場合は全シナリオを未演習として扱います。 |

対応者からの質問に答えるために必要な場合、すべての skill / agent は `./ref` と `./ops` を参照してよいです。ただし参照は「ある情報が観測可能・開示可能か」を判断する目的に限り、開示してよいのは現在または過去のタイムライン上で観測可能な事実だけです。次に確認すべき手順・監視項目・調査方法といった"手がかり"は、手順書や仕様に載っていても開示しません（対応者自身に調べさせる）。開示は観測可能な事実の提示に留め、GM 自身の推測・仮説・次にやるべき切り分け手順の提案・誘導は含めません（推論は対応者に委ねる）。また、設計・仕様・用語の説明を求める質問には説明せず「現時点ではわかりません」「お答えできません」で返し、「〜を確認すると切り分けられます」のような確認先・切り分け方法の示唆や回答先の案内もしません。能動通知も観測事実だけを述べ、「〜が必要」等の示唆表現を含めません。

## 訓練モード
演習開始時に、シナリオ選択の前に**訓練モード**を選びます。

- **全体訓練（既定）**: 対応者1人が全部門の対応を担う既存のモード。モードを選ばずにシナリオを指示した場合も全体訓練として扱います。
- **個別訓練**: 対応者は1部門（自部門）だけを担当し、自部門以外は AI が NPC として能動対応します（NPC は持ち場を自動処理し、必要に応じて自部門へ対応要請を送る）。自部門は初動対応部署のことも、NPC からの要請で動く受動対応部署のこともあります。個別訓練では自部門を尋ね、自部門が初動対応部署または受動対応部署のいずれかに含まれるシナリオを推薦します（受動対応部署は `SCENARIO-LIST.tsv` の GM 内部列で、規模・原因のヒントになるため参加者へは表示しません）。NPC の挙動は事前生成データを増やさず、既存タイムラインを GM が部門単位で実行時に解釈して即興で生成します。

訓練モードと自部門は `01a-select-scenario` が `situation.tsv`（`training_mode` / `primary_department`）へ記録し、`06`・`07`・`10`・`12` がそれを読んでモードに応じて振る舞います。

## シナリオ選定
既定の主経路は、対応者の所属部署によるおすすめ選択です。操作者には、対応者の所属部署でおすすめ候補を絞り込んで選ぶか、シナリオIDを明示指定するか、（フォールバックとして）無作為に選定するかを選ばせます。シナリオを選ぶ際は `01b-list-scenarios` skill で操作者向け一覧（ID＋初動対応部署＋最初の開示可能イベント）を確認でき、所属部署キーワードを渡せば初動対応部署で絞り込んだおすすめ候補を提示できます（個別訓練では初動対応部署または受動対応部署で絞り込み、自部門が初動または受動で関与するシナリオを候補にします）。

1. おすすめ選択では、対応者の所属部署をキーワードに `01b-list-scenarios` で初動対応部署を絞り込み、候補（ID＋初動対応部署＋最初の開示可能イベント）から操作者が1つを選ぶ。選んだIDは明示指定として扱う（全体訓練ではその部署が初動を担うシナリオ、個別訓練では自部門が初動または受動で関与するシナリオになる）
2. 指定シナリオID（おすすめからの選択・明示指定のいずれでも）が渡された場合、AIは無作為選定をせずそのシナリオを主シナリオに採用する（明示指定なので演習済みID一覧より優先する）。事前生成済みシナリオの指定なら、生成/再利用の確認は省略し再利用モードを採用する
3. 所属部署を決められない、または所属部署の一致が0件で操作者がシナリオを選ばない場合に限り、無作為選定にフォールバックする。演習済みシナリオID一覧が渡されていれば `SCENARIO.tsv` から該当IDを除外し、残った未演習シナリオを `shuf` コマンド等で無作為順に並べ、先頭から今回の主シナリオを1つ選ぶ
4. AIは主シナリオの `同時発生候補ID` や状況設定から、同時に発生が想定されるシナリオがあれば追加で選ぶ
5. 主シナリオと同時発生シナリオを合わせて「状況」とする。状況は開示不能情報とする

## ステップ
各ステップは個別の skill または agent として実装できる単位にします。統合 skill はこれらを順番に呼び出しますが、デバッグ時は任意のステップだけを中間ファイルから再実行できるようにします。

制御用 skill は `.ai/skills/` 配下に配置し、context を広く使う agent は `.ai/agents/` 配下に配置します。AIが参照する共通仕様は `.ai/shared/` 配下に配置し、会話用プロセスの実装は `tools/ttx-human` に配置します。

ステップ2の理想タイムラインは、演習開始時にユーザーが選ぶモードに応じて、その場で**アドホック生成**するか、事前生成済みの `timelines/SCN-xxx/TIMELINE-1.tsv` を**再利用**します。テンポを重視する場合は生成コストの小さい**再利用モードを推奨**します。ステップ3〜5の想定質問集・想定回答集は、そのときの現在タイムラインから生成します。事前生成の `QUESTIONS-1.tsv` / `ANSWERS-1.tsv` は参考資料です。末尾の `-1` はバージョン1の意味で、対応者の行動により現在タイムラインは `-2`, `-3` … と理想から分岐していきます。下記の番号付きステップは概念的な流れを示します。

演習はテンポが重要なため、ライブの質疑・行動ループでは GM の応答を端的にし、過度に考え込まないようにします。応答が遅い場合は、モデルは下げずに reasoning effort を下げることで高速化できます（詳細は `.ai/skills/00-run-exercise/SKILL.md` の「応答速度の方針」）。

1. AIはシナリオ選定ルールに従って状況を設定する
2. AIは状況と観測情報一覧をもとに、状況の時間的進展と理想的な対応者の行動を予測し、時刻、イベント、開示可能情報、開示不能情報のタイムラインにまとめる。このタイムラインは理想タイムラインとする。理想タイムラインは開示不能情報とする
3. AIは理想タイムラインのイベントごとに想定質問集を作成する。想定質問集は開示不能情報とする
4. AIは想定質問集に想定回答を付記して想定回答集を作成する。想定回答集は開示不能情報とする
5. AIは想定回答集と理想タイムラインを照合し本来知り得ない情報にもとづく回答がないか確認する。本来知り得ない情報にもとづく回答があれば、想定回答から本来知り得ない情報を削除する
6. AIは理想タイムラインの最初のイベントを対応者に開示する。理想タイムラインをコピーして現在タイムラインとする。現在タイムラインの未来部分は開示不能情報とする。過去・現在部分に含まれる開示可能情報のみ開示してもよい（個別訓練で自部門が受動対応部署のときは、生の初動アラートではなく初動部署＝NPC からの対応要請を起点に開示する）
7. AIは対応者からの質問と行動を受け付ける。質問について開示不能情報でなければ開示し（ただし観測可能な事実の提示に留め、原因・影響の推測や次にやるべき切り分け手順の提案・誘導は含めず、推論は対応者に委ねる）、開示不能情報である場合はわからないと答える。行動については現在タイムラインに行動イベントを追加し、行動に応じた状況の進展と未来の予測を新しい現在タイムラインとして作成する（個別訓練では対応者の質問・行動を自部門のものとして解釈し、自部門以外の理想アクションは NPC が即興処理したものとして反映する）
8. 現在タイムラインと新しい現在タイムラインの差分からAIは想定回答集を更新する
9. AIは想定回答集と新しい現在タイムラインを照合し本来知り得ない情報にもとづく回答がないか確認する。本来知り得ない情報にもとづく回答があれば、想定回答から本来知り得ない情報を削除し、新しい想定回答集を更新する
10. AIはタイムラインの次のイベントに進む。AIは能動的通知があれば対応者に通知する。AIは能動的通知がなければ何もしない（個別訓練では自部門宛の能動通知や NPC からの対応要請を送り、自部門に無関係な NPC の自動処理は通知せずカーソルだけ進める）
11. 次イベントがなくなるまで7に戻る。次イベントがなくなったら12に進む
12. タイムラインの最終版からポストモーテムを作成し、ユーザーに開示する（`/giveup` での終了時も同様。ただし `/abort` で中断した場合はポストモーテムを作成せず、中断通知だけを出して終了する）

## 中間ファイル出力
ゲームマスター自身のデバッグと差分確認のため、AIは理想タイムライン、現在タイムライン、想定質問集、想定回答集を中間ファイルとして保存します。ステップ別 skill または agent の入出力も中間ファイルとして保存し、前段の出力を後段の入力として再利用できるようにします。

理想タイムライン（バージョン1）は、アドホック生成または事前生成 `timelines/SCN-xxx/TIMELINE-1.tsv` の再利用で用意します。中間ファイルは `.ai/runs/<run-id>/` に `TIMELINE-<N>.tsv`（版1＝理想、最新＝現在タイムライン）、`QUESTIONS-1.tsv`、`ANSWERS-<N>.tsv`、`REVIEWED-ANSWERS-<N>.tsv` などの名前で保存します。命名とバージョンの詳細は `.ai/shared/references/data-formats.md` を参照します。

中間ファイルには開示不能情報や未来情報が含まれるため、演習中に対応者へ開示してはいけません。ポストモーテム作成時に必要な範囲だけを整理して開示します。

IPC ログも中間ファイルとして保存します。公開ログには人間に表示された質問、回答、通知、行動だけを記録し、内部ログにはゲームマスター側のステップ実行結果、開示判定、デバッグイベントを記録します。内部ログは演習中に対応者へ開示してはいけません。

## フォーマット
### シナリオ一覧
`SCENARIO.tsv` を元に、別セッションで `./ref` 配下の仕様・設計文書を参照して肉付けします。

既存の `ID`、`シナリオ`、`元リスク事象ID` は維持し、次の列を追加します。

```tsv
ID	シナリオ	元リスク事象ID	影響機能	影響業務	主要コンポーネント	依存システム	想定原因	顧客影響	業務影響	データ影響	重大度目安	同時発生候補ID	調査観点	復旧・緩和候補	参照文書
```

* `ID` は `SCN-001` のようなシナリオID
* `元リスク事象ID` は元になったリスク事象ID。複数ある場合は `;` 区切り
* `同時発生候補ID` は同時に発生しうるシナリオID。複数ある場合は `;` 区切り
* `参照文書` は根拠にした `./ref` 配下のファイルパス。複数ある場合は `;` 区切り
* 根拠が見つからない項目は推測で埋めず、空欄にする

### 観測情報一覧
別セッションで `./ops` 配下の障害対応手順書・監視手順・Runbook から洗い出します。

```tsv
観測ID	観測種別	名称	対象システム	対象機能	取得元	確認方法	正常時の目安	異常時の例	関連シナリオID	能動通知対象	対応者質問時に開示可	開示条件	参照手順書
```

* `観測ID` は観測情報を一意に識別するID
* `観測種別` は `PagerDuty`、`Datadog`、`ログ`、`CS問い合わせ`、`SNS`、`外部ステータス` など
* `関連シナリオID` は関連する `SCENARIO.tsv` のID。複数ある場合は `;` 区切り
* `能動通知対象` はアラートやCS検知のように、対応者へ能動的に通知する情報なら `yes`、質問されるまで開示しない情報なら `no`
* `対応者質問時に開示可` は対応者から質問された場合に開示してよい情報なら `yes`、開示不能なら `no`
* `開示条件` は「当該時刻以降」「該当メトリクスを質問された場合」「CS確認後」など、情報を開示できる条件
* `参照手順書` は根拠にした `./ops` 配下のファイルパス。複数ある場合は `;` 区切り

### 状況
シナリオIDの集合。

### タイムライン
時刻、イベント、開示可能情報、開示不能情報、想定対応部署の5列からなるTSV（`開示不能情報` と `想定対応部署` は GM 内部の非表示列）。
タイムラインは差分を捉えたいので変更があった場合は別ファイルに保存する。ファイル名は `タイムライン_<version>.tsv` 形式とする。`<version>` はタイムラインのバージョン番号で、1から始まる自然数とする。

* 時刻は `YYYY-MM-DD HH:MM:SS` 形式のISO 8601 時刻
* イベントは、(1)対応者への能動的情報開示（PagerDuty 等のアラートの発火や CS からの SNS 炎上検知など）、(2)対応者に伝えない状況の変化、(3)対応者のアクション、のいずれか
* 開示可能情報は観測情報の値。対応者から質問があれば開示する。ない場合は空でOK
* 開示不能情報は観測情報以外の情報。対応者には質問があっても開示しない。ない場合は空でOK
* 想定対応部署はその行の一次対応を担う部署の集合（GM内部・非表示）。集合表記（`{}` / `{SRE}` / `{A, B}`）で書き、個別訓練の NPC／自部門ルーティングと、`SCENARIO-LIST.tsv` の受動対応部署の決定的導出（初動対応部署は最初の可視イベント由来の既存ロジックで判定）に使う。詳細は `.ai/shared/references/data-formats.md`「タイムライン」節を参照

### 想定質問集
時刻、質問の2列からなるTSV。

* 時刻は `YYYY-MM-DD HH:MM:SS` 形式のISO 8601 時刻
* 質問は対応者が質問する可能性のある質問

### 想定回答集
時刻、質問、回答の3列からなるTSV。

* 時刻と質問は想定質問集をそのまま維持する（=回答列だけ追加）
* 回答は質問に対する回答

### ポストモーテム
以下のフォーマットのMarkdownファイル。

```markdown
# ポストモーテム
今回の障害対応机上演習のポストモーテムです。

## 設定された状況
状況を3行程度で書く。

## 実際のタイムライン
タイムラインの最終版をMarkdownの表形式で書く。

## 改善提案（総評）

## 詳細評価

## 要確認事項

| --- | --- | --- | --- | --- | --- |
| 記入 | 記入 | 記入 | 記入 | 記入 | 記入 |
```
