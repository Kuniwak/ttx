# Agent: シナリオ一覧の事前生成

このagentは演習の直線フローには属しません。操作者がシナリオを選びやすいよう、シナリオ一覧 `SCENARIO-LIST.tsv` を事前生成・更新するためのフロー外バッチです。`timelines/` の事前生成と同じ位置づけで、シナリオや事前生成タイムラインを追加・変更したときに再実行して一覧を最新化します。

シナリオを1件追加する `.ai/skills/92-build-scenario/SKILL.md` は、最終ステップでこのagentを呼び `SCENARIO-LIST.tsv` を更新します。差分の1行追記ではなく**全件再生成**で呼ぶことで、並び・件数・初動対応部署の判定を常に `SCENARIO.tsv` と整合させ、統廃合（既存シナリオの統合・タイムライン変更）にも追従させます。

生成した `SCENARIO-LIST.tsv` は表示用skill `.ai/skills/01b-list-scenarios/SKILL.md` が提示します。表示用列（`ID` / `初動対応部署` / `最初の開示可能イベント`）は**公開可能情報**として作るため、`シナリオ` 概要（原因のネタバレになりうる）は載せず、`開示可能情報` の要約と、その初動対応部署だけを載せます。`初動対応部署` は操作者が対応者の所属部署でシナリオを絞り込む「おすすめ選択」のキーになります（`.ai/skills/00-run-exercise/SKILL.md` ステップ2、`.ai/skills/01b-list-scenarios/SKILL.md`）。個別訓練では `受動対応部署`（GM内部専用の非表示列）も絞り込みキーに加わり、自部門が `初動対応部署` または `受動対応部署` のいずれかに含まれるシナリオを推薦します。

## 言語

イベント要約は日本語で書きます。技術識別子（観測ID・コンポーネント名など）は元資料のまま使ってかまいません。

## 入力

- `SCENARIO.tsv`（全シナリオのID）
- 各 `timelines/<SCN>/TIMELINE-1.tsv`（理想タイムラインのバージョン1。末尾の `想定対応部署` 列から `受動対応部署` を決定的に導出する）
- `OBSERVATION.tsv`（最初の可視イベントの初動対応部署を判定する根拠。`観測種別` / `対象システム` / `取得元` を参照）
- `.ai/shared/references/data-formats.md`

## 出力

- リポジトリルートの `SCENARIO-LIST.tsv`（既存があれば全面再生成）
- 内部ログの記録（任意。フロー外実行のため `.ai/runs/<run-id>/` が無い場合は省略可）

`SCENARIO-LIST.tsv` は次の列で書きます。表示用列（参加者へ提示してよい）は `ID` / `初動対応部署` / `最初の開示可能イベント` の3列で、`受動対応部署` は**末尾**に置く GM 内部専用の非表示列です（表示用3列の位置を変えず末尾に追加する）。

```tsv
ID	初動対応部署	最初の開示可能イベント	受動対応部署
```

- `ID`: `SCENARIO.tsv` のシナリオID。**（表示用列）**
- `初動対応部署`: 当該シナリオの最初の可視イベントを初動で受け取る/対応する部署。`;` 区切り。後続で関与する部署は載せない。**（表示用列）**
- `最初の開示可能イベント`: 当該シナリオの `TIMELINE-1.tsv` で最初に開示できる観測情報の1〜2行要約。**（表示用列）**
- `受動対応部署`: 当該シナリオで、初動対応部署以外に、NPC からの対応要請を受けて能動的に対応する部署（個別訓練の受動対応者になりうる部署）。`;` 区切り。該当が無ければ空。判定基準は手順3.5。**GM 内部専用の非表示列**（後続関与部署は規模・原因のヒントになるため参加者へは出さない。個別訓練のおすすめ絞り込み専用）。

## 手順

1. `SCENARIO.tsv` を読み、全シナリオIDを得る。
2. 各シナリオについて `timelines/<SCN>/TIMELINE-1.tsv` を読む。`06-disclose-first-event` と同じ判定で、`開示可能情報` に実際の観測情報が現れる最初のイベントを特定し、その `開示可能情報` だけを1〜2行に要約する。
   - `イベント` 列（隠れた状態変化を含みうる）と `開示不能情報` 列は要約に使わない。
   - `開示可能情報` が「現時点では開示可能な情報はまだない」等、観測情報の不在を述べるだけの行は飛ばし、観測情報が実際に現れる最初の行を使う。
   - 観測ID（`OBS-xxx`）は一覧では提示不要なので要約に含めない。何が観測されたか（アラート発火元・メトリクス・問い合わせ内容など）だけを書く。
   - `TIMELINE-1.tsv` が無いシナリオは「最初の開示可能イベント」を `事前生成なし` とする。
   - どのイベントにも開示可能な観測情報が無い場合は `開示可能情報なし` とする。
3. 手順2で特定した最初の可視イベントの**初動対応部署**を判定し `初動対応部署` にする。判定根拠は、その最初の可視イベントの内容（アラート発火元・チャンネル・問い合わせ種別など）と、その行が参照する `OBS-xxx` を `OBSERVATION.tsv` で引いた `観測種別` / `取得元` / `対象システム` の**部署相当トークンだけ**を使う。
   - 監視アラート（`Prometheus` / `Grafana` アラート / オンコール通知 由来）で最初に検知されるなら初動はオンコールの `SRE`。
   - 発信源が業務チャネルや部署なら、その部署/ロールにする。例: ユーザー問い合わせ / サポートチケット → `カスタマーサポート`、影響サービスのオーナーチームへの連絡 → `開発`、対外周知・広報の起点 → `広報`。
   - システム名・ベンダー名（`frontend` / `paymentservice` / `cartservice` / `checkoutservice` / `valkey` / `kafka` / `postgres` 等）は部署ではないので `初動対応部署` に入れない。
   - 表記揺れは正規形に正規化する（例 `CS対応` / `サポート` → `カスタマーサポート`、`Dev` / `サービスチーム` → `開発`）。
   - 初動が真に複数部署で共同のときだけ `;` で複数並べる。判定できないときは `不明`、`最初の開示可能イベント` が `事前生成なし` / `開示可能情報なし` のときはそれに合わせる。
   - **後続で関与する部署は含めない**（最初の可視イベントの初動対応部署だけ）。
3.5. **受動対応部署を導出する**（GM内部専用の非表示列）。同じ `timelines/<SCN>/TIMELINE-1.tsv` の各行末尾の **`想定対応部署` 列**（集合表記。`.ai/shared/references/data-formats.md`「タイムライン」節）を全行ぶん集めた和集合から、手順3の `初動対応部署` を除いたものを `受動対応部署` とする（＝初動以外で、いずれかの行の一次対応に参加する部署）。順序はタイムラインでの初出順、`;` 区切り。和集合が初動だけ（または空）なら `受動対応部署` は空にする。
   - `想定対応部署` 列は各行の一次対応に参加する全部署を集合表記（`{}` / `{SRE}` / `{開発, カスタマーサポート}`）で保持しているので、受動対応部署はその列からの**決定的な集合演算**で得られる（`イベント` 列プロセス文の再解析や個別の actor/言及判定は不要）。部署名の正規化・システム名/ベンダー名の除外・協調関与（招集・共有・連携先）の取り込みは `想定対応部署` を作る時点（`02-build-ideal-timeline` / `94-build-canonical-timeline`、`data-formats.md`）で済んでいる。
   - `TIMELINE-1.tsv` が無い、または `想定対応部署` 列を持たない旧形式のシナリオは `受動対応部署` を空にする（`最初の開示可能イベント` が `事前生成なし` / `開示可能情報なし` のシナリオも空）。
4. `ID` / `初動対応部署` / `最初の開示可能イベント` / `受動対応部署` の列で `SCENARIO-LIST.tsv` を書き出す。`SCENARIO.tsv` と同じ並び・同じシナリオ数にする。表示用3列（`ID` / `初動対応部署` / `最初の開示可能イベント`）の位置は従来どおり保ち、`受動対応部署` は末尾列に置く。

## 開示ルール

`SCENARIO-LIST.tsv` の**表示用列**（`ID` / `初動対応部署` / `最初の開示可能イベント`）は**公開可能情報**です（参加者へ提示してもよい）。そのために、表示用列の各行は `開示可能情報` 列の要約と、その初動対応部署だけで構成します。末尾の `受動対応部署` 列は**GM内部専用の非表示列**で、参加者へは出しません（`01b` も表示せず、個別訓練のおすすめ絞り込みだけに使う）。`SCENARIO-LIST.tsv` をファイルごと参加者へ共有せず、参加者へ出すのは `01b` の整形済み表示用3列だけにします。

`初動対応部署` に載せてよいのは**最初の可視イベントの初動対応部署だけ**です。後続で関与する部署まで並べると、事案の規模・原因のヒントになり公開できなくなります（初動部署は最初の可視イベントから既に示唆されるためネタバレになりません）。

`シナリオ` 概要（原因のネタバレ）、`イベント` 列の隠れた状態変化、`開示不能情報`（主シナリオID表明、隠れた原因、未来イベント、`scenarios/`・`ops/`・`ref/` などの内部パスや内部メモ）は含めてはいけません。これらが混ざると公開できなくなります。

## 個別デバッグ

同じ `SCENARIO.tsv` と `timelines/` で再実行すると、同じ `SCENARIO-LIST.tsv` になることを確認します。
