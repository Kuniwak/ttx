# Agent: 理想タイムライン作成（canonical）

このagentは `.ai/skills/92-build-scenario/SKILL.md` の**理想タイムライン作成・自己評価の段**で使います。新規シナリオの理想タイムライン（バージョン1）を `timelines/<新ID>/TIMELINE-1.tsv` として新規生成し、`EVAL_CRITERIA.md` に照らして自己評価・改善してから確定します。

演習用 agent `.ai/agents/02-build-ideal-timeline.md` の**アドホック生成モード**と同じ作業を、演習作業ディレクトリ `.ai/runs/<run-id>/` ではなく canonical 正本 `timelines/<新ID>/` に対して行います。開示可否の判定基準（`開示可能情報` と `開示不能情報` の切り分け、手がかり・推測・誘導の禁止）は `.ai/agents/02-build-ideal-timeline.md` の「ref / ops の参照」「開示ルール」に従い、ここでは重複定義しません。

## 言語

タイムライン内で人間に見せうる情報（列2の能動通知本文・列3の `開示可能情報`）は日本語で書きます。内部メモ（列4）には元資料の技術識別子をそのまま使ってかまいません。

## 入力

- 対象シナリオID（92 が採番済み）と `scenarios/<新ID>`・`SCENARIO.tsv` の当該行
- 93 が返した `参照した根拠` パス
- `OBSERVATION.tsv`（観測ID・能動通知対象・開示条件・参照手順書）
- `ops/incident-handling-manual.md`（重大度・エスカレーション先・PII運用の判断基準）
- 必要な `./ops` 配下の障害対応手順書・監視手順・Runbook
- 必要な `./ref` 配下の仕様・設計・要求文書
- `EVAL_CRITERIA.md`
- `.ai/shared/references/data-formats.md`（タイムライン列構成・先頭データ行の重大度・エスカレーション注記規約）

## 出力

- `timelines/<新ID>/TIMELINE-1.tsv`（列: 時刻 / イベント / 開示可能情報 / 開示不能情報 / 想定対応部署。末尾の `想定対応部署` は GM 内部の非表示列）
- 内部ログの記録（自己評価の所見。フロー外のため `.ai/runs/` が無ければ省略可）

## 手順

1. シナリオ理解に必要な参照文書（`scenarios/<新ID>`・93の根拠・関連する `./ref`・`./ops`）を読む。
2. 観測可能な変化（能動通知・問い合わせ・監視確認）と、対応者に伝えない内部状態変化を時系列で作る。`OBSERVATION.tsv` の `能動通知対象`／`開示条件` を尊重し、観測ID（`OBS-xxx`）を `開示可能情報` に結び付ける。
3. 影響を最小化する理想的な対応者アクションを含める。`ops/incident-handling-manual.md` が当該規模・種別で必須とする対応を漏らさない（**RP-3**）。例: 顧客影響のあるサービス停止は SEV を引き上げてインシデントコマンダーを招集し、定期的なステータス更新（社内告知・ステータスページ）を出す。セキュリティ／データ事案は顧客個人情報（PII）の扱い（限定共有チャネルの利用、最小権限でのアクセス、PII を含む情報の取り扱い分離）を理想対応に反映する（**RP-6**）。
4. 未来イベント・原因・隠し状況は `開示不能情報`（列4）に入れる。参加者向け面（列2の能動通知本文・列3の `開示可能情報`）には観測された事実だけを書き、「〜が必要」「〜の確認が必要」「〜の要否」「〜を検討してください」等の手がかり・誘導・推測を入れない（**RP-1**。02 の開示ルールに従う）。
4.5. 各行に末尾列 `想定対応部署`（列5・GM内部・非表示）を付け、その行の一次対応を担う部署を**集合表記**で書く（`{}` / `{SRE}` / `{開発, カスタマーサポート}`）。判定・語彙は `data-formats.md`「タイムライン」節に従う（`理想アクション: <部署>が…` はその部署、`能動通知` は受けて一次対応する部署＝監視アラートは初動対応部署、汎用的な「対応者が…」の指揮・宣言行は初動対応部署、`隠れた状態変化` は `{}`）。これは `90-build-scenario-list` が `初動対応部署`・`受動対応部署` を決定的に導出する典拠になる。
4.6. 各イベントの `開示可能情報`（列3）と能動通知本文（列2）は**そのイベント時点で新たに観測可能になる事実を中心**に書く。複数イベントが同じ観測ID（`OBS-xxx`）を共有してよいが、**能動送信される `能動通知:` イベントどうしが同一 OBS-ID を共有する場合**は、後続イベントの開示文を**新たな進展（差分）主題**にし、既出観測の再掲で参加者に「同じ通知の再送」と誤認させない（**RP-8**。02 の開示ルール「開示文の粒度」に従う。`理想アクション:` / `状況変化:` は演習中に能動送信されないので再送誤認の対象外だが、各イベント時点の新規観測中心に書く方針は同じ）。
5. **真因が直近のデプロイ/変更のシナリオ**では、変更／デプロイが起きた事実自体は履歴・操作ログで見える観測事実なので、調査ステップの `開示可能情報` に「直近に〈対象〉の変更／デプロイがあったことを確認できる」を記載する（不具合の中身は `開示不能情報` に温存）。外部障害・相場変動・データ/バッチ・攻撃・定常運用・NW劣化など真因が変更でないシナリオには付けない（**RP-4**）。
6. **先頭データ行（隠れた発端＝最初の状況変化の行）の `開示不能情報`（列4）末尾に重大度・エスカレーション注記を書く**（`data-formats.md`「先頭データ行の重大度・エスカレーション注記」）。`ops/incident-handling-manual.md` を根拠に、`根拠:` ／ `対応手順書: ...（governing: <主たる手順書>）` ／ `重大度: <SEV1 / SEV2 / SEV3>（事由: ...）` ／ `エスカレーション先: ...` を記す（**RP-2**）。governing 手順書は症状・真因と整合させ、無関係な旧手順書を残さない（**RP-7**）。
7. 先頭注記の確度（例「SEV1」と断定）と本文の理想アクションの確度（例「重大度は要判断」と留保）の表現を一致させる（**RP-5**）。
8. できあがったタイムラインを `EVAL_CRITERIA.md` の評価項目に照らして自己評価し、評価値を上げられる箇所（検知〜復旧の時間短縮、影響範囲の特定、状況認識・原因切り分け、対応判断・復旧実行、コミュニケーション・レポーティング、ガバナンス・エスカレーション、記録・事後改善）を改善してから確定する。
9. `timelines/<新ID>/TIMELINE-1.tsv` として保存する。

## 開示ルール

このagentが作るファイルは内部情報です。`開示不能情報`（列4）・`想定対応部署`（列5）と未来部分は、演習時に開示ゲート（`.ai/skills/06-disclose-first-event/SKILL.md`）と `90-build-scenario-list` が公開フィールドだけを取り出すまで開示しません。先頭行の重大度・エスカレーション注記は列4（非開示）にのみ書き、`想定対応部署`（列5・非開示）とともに参加者向け面には出しません。

## 個別デバッグ

同じシナリオ定義・観測情報・参照文書・`EVAL_CRITERIA.md` で再実行し、評価基準に照らして改善余地が無くなっていることを確認します。
