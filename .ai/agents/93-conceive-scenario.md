# Agent: シナリオ着想

このagentは `.ai/skills/92-build-scenario/SKILL.md`（フロー外のシナリオ追加スキル）の**シナリオ着想の段**で使います。1つの入力（障害対応手順書 `ops/<番号>.md` / `INCIDENTS.tsv` の1行）から、関連する要求・仕様・設計・インシデント対応マニュアルを精査し、机上演習に使えるシナリオを1つ着想します。あわせて、既存シナリオとの重複を判定します。

このagentは演習中ではなく canonical 正本を整備するためのものなので、IPC（`ttx-*`）は使いません。判断材料が足りないときは 92 スキル経由で操作者に確認します。

## 言語

`シナリオ` 本文は日本語で書きます。技術識別子（観測ID・コンポーネント名・手順書パスなど）は元資料のまま使ってかまいません。

## 入力

- 正規化済みの単一入力 `{input_kind, source_ref, seed_risk_id}`（92 スキルが用意）
  - `input_kind`: `ops` / `incident`
  - `source_ref`: `ops/<番号>.md` パス、`INCIDENTS.tsv:N` のいずれか
  - `seed_risk_id`: `元リスク事象ID` の暫定値（incidentでは確定値、opsでは未定のことがある）
- `SCENARIO.tsv`（既存シナリオ全行。重複判定と `元リスク事象ID` 採番に使う）
- `OBSERVATION.tsv`（`参照手順書` 列で ops と観測のひも付けを引く。観測の `関連シナリオID` から既存シナリオを引き当てる）
- `INCIDENTS.tsv`（incident入力のとき該当行）
- `ops/incident-handling-manual.md`（インシデント対応マニュアル）
- 必要な `./ops` 配下の障害対応手順書・監視手順・Runbook
- 必要な `./ref` 配下の仕様・設計・アーキテクチャ資料
- `.ai/shared/references/data-formats.md`

## 出力

このagentはファイルを書きません。次を 92 スキルへ返します（採番・書き出しは 92 が決定的に行う）。

- `シナリオ`: 障害の振る舞いを1文程度で表す本文（`SCENARIO.tsv` の `シナリオ` 列に入る粒度。原因の断定ではなく「何が起きているか」を書く。既存シナリオのトーンに合わせる）
- `元リスク事象ID`: 入力種別に応じた規約値（`data-formats.md`「`元リスク事象ID` の値規約」に従う）。手順書入力では `OPS-CASE-*`／`OPS-FREQ-*` のどちらの規約に当たるかを**提案**する（次番号の確定採番は 92 スキルが決定的に行う）。どちらでもない／根拠不足なら空欄。
- `重複判定`: `new` / `duplicate-of:SCN-NNN` / `consolidate-into:SCN-NNN` のいずれかと、その根拠
- `参照した根拠`: 着想の根拠にした `scenarios/`・`ops/`・`ref/` パス（94 の先頭行注記に渡す）

## 手順

1. 入力種別ごとに一次資料を読む。
   - `ops`: `source_ref` の手順書本文を読み、`OBSERVATION.tsv` の `参照手順書` でその手順書にひも付く観測を集める。
   - `incident`: `INCIDENTS.tsv:N` の行（事象・原因・出典）を読む。
2. 関連する要求・仕様・設計（`./ref`）とインシデント対応マニュアル（`ops/incident-handling-manual.md`）を精査し、対象システム（`ref/` のサービスカタログ）で同種の障害が起きたときに「何が観測され、何が起きるか」を1つのシナリオとして構想する。原因そのものではなく、観測される障害の振る舞いを `シナリオ` 本文にする。
3. **重複判定**を行う。
   1. `seed_risk_id` が既存 `SCENARIO.tsv` の `元リスク事象ID`（`;` 分割）に既出なら `duplicate-of:<該当SCN>`。
   2. `ops` 入力で、その手順書にひも付く観測の `関連シナリオID` が特定の既存シナリオに強く集まるなら類似を疑い、新規性を本文で正当化できるか確認する。
   3. 構想した `シナリオ` 本文を既存 `シナリオ` 本文と突き合わせ、実質的に同一の障害なら `duplicate-of:`、既存行へ `元リスク事象ID` を統合すべきなら `consolidate-into:` と判定する。
4. `元リスク事象ID` を確定する（上記「出力」の規約）。
5. 着想の根拠にしたパスを列挙する。

## 開示ルール

このagentの出力は内部情報です。`シナリオ` 本文・`元リスク事象ID`・根拠パスはいずれも参加者へ出す面（`SCENARIO-LIST.tsv` の最初の開示可能イベント等）には載りません（一覧へ載るのは 90 が抽出する最初の開示可能イベントの要約と初動対応部署だけ）。

## 個別デバッグ

同じ正規化入力と同じ `SCENARIO.tsv` で再実行すると、同じ `シナリオ` 本文・`元リスク事象ID`・重複判定になることを確認します。
