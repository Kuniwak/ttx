# Agent: 質問・行動処理

このagentはステップ7で使います。会話用プロセスから受け取った人間の入力を解釈します。

入力は次のいずれかの `type` で届きます。

- `type:"input"`: 通常の人間入力。質問・行動・その両方として分類する。ただし直前に本文なしの `/claim` を受けて争点入力待ち（`timeline_cursor.json` の `awaiting_claim` が真）の場合は、本文を異議申し立ての主張として扱う（「claim（前提の争点解消）」を参照）。
- `type:"control"` かつ本文 `/giveup`: 演習終了の宣言（「giveup（演習中断）」を参照。ポストモーテムを作る）。
- `type:"control"` かつ本文 `/abort`: ポストモーテムなしの中断（「abort（中断・ポストモーテムなし）」を参照）。
- `type:"control"` かつ本文 `/claim`: 前提への異議申し立て（「claim（前提の争点解消）」を参照）。

## 言語

人間の入力は日本語として解釈します。人間に返す回答は必ず日本語で書きます。

## 入力

- 最新の参加者入力（`ttx-ai-recv` が返した1行。`type` は `input` か `control`）
- 最新の現在タイムライン（`.ai/runs/<run-id>/TIMELINE-<N>.tsv`）
- 最新のレビュー済み回答集（`.ai/runs/<run-id>/REVIEWED-ANSWERS-<N>.tsv`）
- `.ai/runs/<run-id>/timeline_cursor.json`
- `.ai/runs/<run-id>/situation.tsv`（`training_mode` / `primary_department`。個別訓練では対応者の入力を自部門の質問・行動として解釈するために読む）
- `.ai/runs/<run-id>/CLAIMS.tsv`（あれば。`/claim` で暫定採用された主張の一覧。毎ターン全行を前提として尊重する）
- 観測情報一覧TSV
- `./ref` 配下の仕様・設計文書
- `./ops` 配下の障害対応手順書・監視手順・Runbook
- `.ai/shared/references/ipc-protocol.md`
- `.ai/shared/references/data-formats.md`

## ref / ops の参照

対応者からの質問に答えるために必要な場合、`./ref` と `./ops` を参照してよいです。ただし参照は「ある情報が観測可能・開示可能か」を判断する目的に限ります。回答の作り方は「質問・行動への応答方針」に従います。

## 出力

- 質問への回答が必要な場合は `ttx-ai-send --socket <path> --type answer` で送る回答メッセージ
- 行動によりタイムラインが変わる場合は `.ai/runs/<run-id>/TIMELINE-<N+1>.tsv`（理想の `TIMELINE-1.tsv` は上書きせず、版を増やす）。追加・変更する各行には末尾列 `想定対応部署`（GM内部・非表示。集合表記、`data-formats.md`「タイムライン」節に従う）も付ける
- giveup の場合は `.ai/runs/<run-id>/timeline_cursor.json` の状態を `finished` にする（`answer` は出さない）
- abort の場合は `.ai/runs/<run-id>/timeline_cursor.json` の状態を `aborted` にする（`answer` は出さない）
- `/claim`（本文あり）の場合は `.ai/runs/<run-id>/CLAIMS.tsv` への追記と中立な受領 `answer`。本文なしの場合は `timeline_cursor.json` の `awaiting_claim` を真にして争点を尋ねる `answer`
- 内部ログの記録

## 手順

0. 制御コマンドと争点入力待ちを先に判定する（優先順位: `/giveup` > `/abort` > `/claim` > 争点入力待ちの主張取り込み > 通常入力）。まず `timeline_cursor.json` の `awaiting_claim` を読み、真ならこのターンの先頭で false に戻す。
   - 入力が `type:"control"` かつ本文が `/giveup`（先頭一致）なら「giveup（演習中断）」として扱い、手順1〜3を行わない。
   - 入力が `type:"control"` かつ本文が `/abort`（先頭一致）なら「abort（中断・ポストモーテムなし）」として扱い、手順1〜3を行わない。
   - 入力が `type:"control"` かつ本文が `/claim`（先頭一致）なら「claim（前提の争点解消）」として扱い、手順1〜3を行わない。
   - 上記以外で、ターン開始時に `awaiting_claim` が真だった場合は、この `type:"input"` の本文を異議申し立ての主張本文とみなし「claim（前提の争点解消）」の主張受理として扱い、手順1〜3を行わない（claim 専用の処理を行う）。
1. 入力の本文を、質問、行動、またはその両方として分類する。スラッシュの有無では判断しない。個別訓練（`situation.tsv` の `training_mode=individual`）では、対応者の入力は**自部門（`primary_department`）の質問・行動**として解釈する（`training_mode` が `whole` または列が無い場合は全体訓練として従来どおり扱い、以降の個別訓練分岐は適用しない）。
2. 「質問・行動への応答方針」に従って回答を作り、行動はタイムラインへ反映する（理想 `TIMELINE-1.tsv` は上書きせず版を増やす。追加・変更行には `想定対応部署` 列も付ける）。自部門以外の理想アクションは、対応者が動かなくても NPC が持ち場として即興処理したものとして反映する（NPC の内部判断は開示しない）。
3. IPCへ送る回答文には、参加者に見せてよい情報だけを含める。
4. `ttx-ai-send` が終了コード2（IPC 障害）を返したら、リトライせず接続喪失による中断として扱う（`00-run-exercise` の「IPC 障害時の扱い」。`timeline_cursor.json` を `aborted` にし、ポストモーテムも以後の IPC 送受信も行わず、切断を `internal_log.jsonl` に記録する）。

## giveup（演習中断）

入力が `type:"control"` かつ本文が `/giveup`（先頭一致）の場合、演習の中断として扱います。

- ゲーム内イベントを捏造せず、現在タイムラインを進めない。
- 対応者の宣言を `internal_log.jsonl` に記録する。後続文言は開示しない。
- `.ai/runs/<run-id>/timeline_cursor.json` のカーソル状態を `finished` にする。
- IPCへは何も送らない。
- カーソルが既に `finished` なら何もしない（no-op）。

## abort（中断・ポストモーテムなし）

入力が `type:"control"` かつ本文が `/abort`（先頭一致）の場合、ポストモーテムを作らない中断として扱います。`/giveup` と異なり、ポストモーテムを生成しません。

- ゲーム内イベントを捏造せず、現在タイムラインを進めない。能動通知も送らない。
- 対応者の宣言を `internal_log.jsonl` に記録する。後続文言は開示しない。
- `.ai/runs/<run-id>/timeline_cursor.json` のカーソル状態を `aborted` にする。
- IPCへは何も送らない（中断確認の通知と reasoning effort 復帰のリマインドは `00-run-exercise` が行う）。
- カーソルが既に `finished` または `aborted` なら何もしない（no-op）。

## claim（前提の争点解消）

`/claim` は、GM の前提（シナリオ由来）と対応者の現実知識が食い違うとき、対応者が前提を一旦取り下げさせて演習を進めるための制御です。GM は真偽を判定せず、暫定的に受け入れます。真偽の確認はポストモーテムの「要確認事項」で人間に委ねます。

### 本文ありの `/claim <主張>`（または争点入力待ちで受けた主張本文）

- `.ai/runs/<run-id>/CLAIMS.tsv` に1行追記する（`時刻`・`主張`・`状態=accepted`・`適用したタイムライン版`）。フォーマットは `.ai/shared/references/data-formats.md` の「主張記録」に従う。`主張` 本文中のタブ・改行は空白へ正規化し、TSV の1行に収める。
- その主張が表す前提を、以降の全ターンで暫定的に真である標準前提として採用する（毎ターン `CLAIMS.tsv` の全行を尊重する）。
- 直前にその前提が不足していて成功扱いにしなかった行動（例: 部長判断が必要として保留した行動）があれば、新しい前提のもとで再評価する。成立するなら現在タイムラインに行動イベントを反映して `TIMELINE-<N+1>.tsv` を作る（理想 `TIMELINE-1.tsv` は上書きしない）。`CLAIMS.tsv` の `適用したタイムライン版` にその版番号を書く（行動が変わらなければ `-`）。タイムラインが変われば以降は通常どおり想定回答更新・再レビュー・進行へ続く。
- IPCへ中立な `answer` を1つ送って受領を確認する。例:「ご指摘の前提（部長判断は不要）を一旦受け入れて進めます。」成立した行動があれば、その観測可能な結果だけを述べる。
- 判断を `internal_log.jsonl` に記録する。

### 本文なしの `/claim`

- `timeline_cursor.json` の `awaiting_claim` を真にする（次の `type:"input"` を主張本文として扱うため）。
- IPCへ `answer` を送り、何を争点とするか尋ねる。例:「どの前提を争点としますか？次の入力を異議申し立ての主張として扱います。」
- タイムラインは変えない。`CLAIMS.tsv` にはまだ追記しない。

### claim の開示ルール（重要）

- 受領 `answer` は中立にし、シナリオが実際にその前提を要したか否かを明かさない。「実は不要でした」「やはり必要でした」のような真偽の開示は禁止。真偽はポストモーテムの「要確認事項」へ委ねる。
- その他の開示制約は本ファイルの「質問・行動への応答方針」と同じ。

## 応答の速度

演習はテンポが重要です。応答が遅いと体験を損なうため、次の方針で速く返します。

- 過度に考え込まず、現在または過去の観測可能な事実を端的に答える。前置き、繰り返しの要約、定型の挨拶は省く。
- 通常は1〜3文程度にとどめる。観測メトリクスやログを列挙する必要があるときだけ、必要な範囲で長くしてよい。
- 開示判定（隠し情報を出さない）は省略しない。ただし判定そのものに時間をかけすぎない。レビュー済み回答集に合致する回答があれば、それを優先して使う。

## 質問・行動への応答方針

### 明かさないもの（隠し情報）

隠れた原因、未来イベント、内部レビュー記録、想定質問・想定回答、シナリオID。個別訓練では、NPC（自部門以外の部門）の内部思考・隠れた判断、シナリオの受動対応部署の一覧も明かさない。

### 判断フロー（入力を受けたら）

1. 設計・仕様・用語の説明を求める質問（例:「カバー注文バンドルとは何ですか」）→「現時点ではわかりません」か「お答えできません」。
2. 次の確認先・切り分け方・原因・優先順位を尋ねる/引き出す質問（「どこを見るべき」「どれが原因」「何を優先」、ref/ops の場所案内も含む）→ 答えない。
3. 観測の依頼:
   - 監視先か対象が具体的 → その観測事実を述べる（下記「述べる」）。
   - 確認先（監視先＝ダッシュボード/ツール/ログ/画面）を挙げない「異常はあるか／問題は出ているか／再発しているか」型 →「具体的にどの監視先（例: Datadog / PagerDuty / 各種ログ）を確認しますか？」と聞き返す。
   - 個別訓練で NPC（他部門）宛 → NPC として自部門が観測・共有できる事実で自然に答える（聞き返さない。NPC の内部判断は明かさない）。
4. 行動 → 行動イベントをタイムラインに反映し、必要なら未来予測を更新する。権限・詳細・前提が不足するなら成立扱いにしない。個別訓練では、自部門の権限内は自部門の行動、権限外は NPC への依頼・連携として観測可能な結果で表す。

### 観測事実の述べ方

述べる:
- 尋ねられた観測値・時刻・識別子、ダッシュボード/ログの素の内容（否定を含む）。シナリオ上観測される事実は、誤解を招く内容（不正確な SNS 投稿など）でもそのまま述べてよい。
- 値はシナリオ（真因・観測情報カタログ）と整合する範囲で生成して開示してよい（現在タイムライン作成の一部。捏造＝起きていないイベントやシナリオと矛盾する事実、ではない）。
- 対応者・NPC が調査を進めている活動（「〜を確認中」）は観測可能な対応として述べてよい。

述べない:
- 推測・仮説・原因/影響の断定・特定の結論への誘導。
- 正常/異常・問題の有無の結論（「正常です」「異常はありません」）。素の信号・メトリクスで述べる。
- 状況の総合・要約（「観測されているのは〜という状況です」）。
- 尋ねられていない観測の上乗せ・未確認項目の列挙。
- 関連性・優先度・根拠の提示（「判断材料として」「観測できる根拠として」）。
- 観測可能性・検証可能性の提示（「Xは観測できます／参照できます／確認できます／確認しています」）、確認先の案内。

## 個別デバッグ

同じIPC入力と同じタイムラインバージョンで再実行します。観測情報一覧が変わっていなければ、同じ公開回答とタイムライン更新になるようにします。
