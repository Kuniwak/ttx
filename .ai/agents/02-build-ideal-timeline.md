# Agent: 理想タイムライン作成

このagentはステップ2で使います。理想タイムライン（タイムラインのバージョン1）を用意します。用意方法は `00-run-exercise` で選んだモードに従います。

- アドホック生成モード（自由度が高いが低速）: 隠し状況と観測情報一覧をもとに、広いcontextを使って妥当な理想タイムラインを新規生成します。
- 事前生成再利用モード（自由度が低いが高速）: 事前生成済みの `timelines/<primary_scenario_id>/TIMELINE-1.tsv` を読み込んで理想タイムラインにします。

いずれのモードでも、できあがった理想タイムラインを `.ai/runs/<run-id>/TIMELINE-1.tsv` として保存します。これがバージョン1であり、初期の現在タイムラインを兼ねます（別コピーは作りません）。

## 言語

タイムライン内で人間に見せうる情報は日本語で書きます。内部メモには、元資料の技術識別子をそのまま使ってもかまいません。

## 入力

- `.ai/runs/<run-id>/situation.tsv`（`primary_scenario_id` と選択モードを取得する）
- 事前生成再利用モードのとき: `timelines/<primary_scenario_id>/TIMELINE-1.tsv`
- `SCENARIO.tsv`
- 観測情報一覧TSV
- 必要な `./ref` 配下のファイル
- 必要な `./ops` 配下のファイル
- `.ai/shared/references/data-formats.md`

## ref / ops の参照

対応者からの質問に答えるために必要な場合、`./ref` と `./ops` を参照してよいです。このagentではタイムライン作成の根拠としても参照できますが、参照文書から得た内部原因や未来の展開は `開示不能情報` 列に入れ、`開示可能情報` 列へ移してはいけません。

## 出力

- `.ai/runs/<run-id>/TIMELINE-1.tsv`（理想タイムライン＝バージョン1＝初期の現在タイムライン）
- 内部ログの記録

## 手順

1. `situation.tsv` を読み、`primary_scenario_id` と選択モードを得る。
2. アドホック生成モードの場合:
   1. 選定シナリオの理解に必要な参照文書だけを読む。
   2. 公開可能な観測変化と、対応者に伝えない内部状態変化を時系列で作る。
   3. 影響を最小化する理想的な対応者アクションも含める。
   4. 未来イベント、原因、隠し状況は `開示不能情報` に入れる。
   4.5. 各行に末尾列 `想定対応部署`（GM内部・非表示）を付け、その行の一次対応を担う部署を**集合表記**で書く（`{}` / `{SRE}` / `{開発, カスタマーサポート}`）。判定と語彙は `data-formats.md`「タイムライン」節に従う（`理想アクション: <部署>が…` はその部署、`能動通知` は受けて一次対応する部署＝監視アラートは初動対応部署、汎用的な「対応者が…」の指揮・宣言行は初動対応部署、`隠れた状態変化` は `{}`）。
   5. 先頭データ行の `開示不能情報` に、GM 内部メモとして、参照する対応手順書（`ops/*.md`）と governing（主たる）手順書、`ops/incident-handling-manual.md` の基準に照らした重大度（SEV1 / SEV2 / SEV3）と事由・エスカレーション先を、事前生成タイムラインと同じ `対応手順書: …（governing: …）。重大度: …（事由: …）。エスカレーション先: …` 形式で明記する。これは演習後にポストモーテムの `参照すべき対応手順書` で参照される（演習中は開示しない）。
3. 事前生成再利用モードの場合: `timelines/<primary_scenario_id>/TIMELINE-1.tsv` を読み込む。見つからない場合は処理を止め、内部ログにエラーを記録する（再利用モードで事前生成が無いシナリオは `01a-select-scenario` で選定対象外にする）。
4. できあがった理想タイムラインを `.ai/runs/<run-id>/TIMELINE-1.tsv` として保存する。これが初期の現在タイムラインになる。

## 開示ルール

このagentが作るファイルは、後続のゲート用skillが公開フィールドをIPCへ送るまで内部情報です。`開示不能情報` 列と `想定対応部署` 列の内容は決してIPCへ送ってはいけません（いずれも GM 内部の非表示列）。

### 開示文の粒度（OBS-ID 重複と「再送」誤認の回避）

各イベントの `開示可能情報`（列3）と能動通知本文（列2）は、**そのイベント時点で新たに観測可能になる事実を中心**に書きます。複数のイベントが同じ観測ID（`OBS-xxx`）を共有してかまいません（同じ観測対象の継続確認）。ただし、**能動送信される `能動通知:` イベントどうしが同一 OBS-ID を共有する場合**は、後続イベントの開示文を**新たな進展（差分）を主題**にし、既出の観測を再掲して参加者に「同じ通知の再送」と誤認させないようにします（観測 ID の継続自体は許容しますが、テキストで delta を明確にします）。`理想アクション:` / `状況変化:` イベントは演習中に能動送信されない（`.ai/skills/10-advance-timeline/SKILL.md`）ため、それらの `開示可能情報` が前後のイベントと OBS-ID を共有しても再送誤認の対象にはなりませんが、質問時の回答に使われるので、各イベント時点の新規観測を中心に書く方針は同じです。

## 個別デバッグ

同じ `situation.tsv`、観測情報一覧TSV、参照文書セット、選択モードで再実行します。選定済みシナリオを変えてはいけません。
