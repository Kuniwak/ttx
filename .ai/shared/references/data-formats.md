# データフォーマット

特に指定がない限り、UTF-8のTSVを使います。隠し情報は内部ファイルだけに保存します。

## 状況

```tsv
selected_at	primary_scenario_id	related_scenario_ids	selection_method	training_mode	primary_department	disclosure
```

`disclosure` は `internal` にします。`selection_method` は選定方法で、`specified`（操作者がシナリオIDを明示指定）/ `seed`（乱数seed指定の再現選定）/ `random`（無作為選定）のいずれかです。

`training_mode` は訓練モードで、`whole`（全体訓練。対応者1人が全部門の対応を担う既存挙動）/ `individual`（個別訓練。対応者は自部門だけを担当し、自部門以外は GM が NPC として能動対応する）のいずれかです。`primary_department` は個別訓練時の対応者の自部門名（`SCENARIO-LIST.tsv` の部署表記に正規化した1つ）で、全体訓練時は空にします。`training_mode` / `primary_department` 列を持たない旧形式の `situation.tsv` を読んだ場合は、`training_mode=whole`・`primary_department` 空（全体訓練）にフォールバックします。

## タイムライン

```tsv
時刻	イベント	開示可能情報	開示不能情報	想定対応部署
```

参加者向け面は `イベント`（列2の能動通知本文）と `開示可能情報`（列3）だけです。`開示不能情報`（列4）と `想定対応部署`（列5）はいずれも **GM 内部の非表示列**で、IPC へ送ってはいけません。`想定対応部署` は**末尾**に置きます（既存4列の位置を変えない）。

- `時刻`: `YYYY-MM-DD HH:MM:SS`
- `イベント`: 能動通知、隠れた状態変化、対応者アクションのいずれか
- `開示可能情報`: 現在または過去になった時点で開示してよい情報
- `開示不能情報`: 隠れた原因、未来情報、シナリオID、内部メモ
- `想定対応部署`: その行の一次対応を担う部署/ロールの集合（GM内部）。**集合表記**で書く（担当なし＝`{}`、単一＝`{SRE}`、複数＝`{開発, カスタマーサポート}`。区切りは `, `）。部署/ロール名は `SCENARIO-LIST.tsv` の `初動対応部署` と同じ正規形（`SRE` / `開発` / `カスタマーサポート` / `インシデントコマンダー` / `広報` 等。Google SRE のインシデント対応体制に準拠）を使い、システム名・ベンダー名（`frontend` / `paymentservice` / `valkey` 等）は入れない。判定: `理想アクション: <部署>が…` はその部署、`能動通知` はそれを受けて一次対応する部署（監視アラートは初動対応部署）、「対応者が…」の汎用的な指揮・宣言行は初動対応部署、`隠れた状態変化` など担当のない行は `{}`。個別訓練の NPC／自部門ルーティング（`06`／`10`）と、`90-build-scenario-list` の `受動対応部署` の決定的導出（`初動対応部署` は最初の可視イベント由来の既存ロジックで判定する）に使う。

先頭データ行の `開示不能情報` には、主シナリオの GM 内部メタ情報として、参照する対応手順書（`ops/*.md`）と governing（主たる）手順書、`ops/incident-handling-manual.md` の基準に照らした重大度・事由・エスカレーション先を `対応手順書: …（governing: …）。重大度: …（事由: …）。エスカレーション先: …` の形式で記載します（事前生成タイムラインも同形式）。これはポストモーテムの `参照すべき対応手順書` の典拠です。演習中は開示しません。

タイムラインは `TIMELINE-<N>.tsv` でバージョン管理します。バージョン1（`TIMELINE-1.tsv`）が理想タイムラインで、初期の現在タイムラインを兼ねます。対応者の行動でタイムラインが理想から変化すると `TIMELINE-2.tsv`, `TIMELINE-3.tsv` … と版が増え、最新版が現在タイムラインです。`TIMELINE-1.tsv` は上書きしません。

## 想定質問集

```tsv
時刻	質問
```

想定質問集は `QUESTIONS-1.tsv` に保存し、内部情報として扱います。

## 想定回答集

```tsv
時刻	質問	回答
```

想定回答ドラフトは `ANSWERS-<N>.tsv`、開示レビュー済み回答は `REVIEWED-ANSWERS-<N>.tsv` に保存します（`<N>` は対象の現在タイムライン版）。開示レビュー記録は `DISCLOSURE-REVIEW-<N>.md` に残します。いずれも内部情報で、IPCの `answer` として選ばれた回答文だけを人間へ見せてよいです。

## 主張記録

`/claim` で対応者が申し立て、GM が暫定的に受け入れた前提を `CLAIMS.tsv` に記録します。内部情報として扱います。

```tsv
時刻	主張	状態	適用したタイムライン版
```

- `時刻`: `YYYY-MM-DD HH:MM:SS`
- `主張`: 対応者が申し立てた前提の本文（例: `部長判断は不要です`）。TSV の列ずれを防ぐため、本文中のタブ・改行は空白へ正規化して1行に収める
- `状態`: `accepted`（暫定採用済み）
- `適用したタイムライン版`: 主張を受けて再評価し生成した `TIMELINE-<N>` の版番号。行動が変わらなければ `-`

GM は各ターンで `CLAIMS.tsv` の全行を暫定的に真である標準前提として尊重します。真偽は演習中に判定せず、ポストモーテムの `要確認事項` で人間に確認させます。

## IPCログ

JSON Linesを使います。

- `public_log.jsonl`: 人間に表示されたメッセージと、人間から入力されたメッセージを記録する。`/help` は `{"type":"help","text":"/help"}` として記録する（ログ専用で、IPCの `type` ではない）。
- `internal_log.jsonl`: ステップ実行、レビュー、デバッグ用メモを記録する。

## タイムラインカーソル

現在タイムラインの進行位置を `timeline_cursor.json` に保持します。内部情報として扱います。

```json
{"timeline_version": 3, "cursor_index": 5, "state": "running"}
```

- `timeline_version`: 参照中の現在タイムライン版（`TIMELINE-<N>.tsv` の `<N>`）。
- `cursor_index`: 進行済みイベントの位置。
- `state`: `running`（進行中）/ `finished`（終了済み）/ `aborted`（中断・ポストモーテム作成なし）。`finished` は、タイムライン終端に到達した場合、または `/giveup` の場合に設定します。`aborted` は `/abort` の場合に設定し、ポストモーテムを作らずに終了することを表します。
- `awaiting_claim`（任意）: `true` のとき、本文なしの `/claim` を受けて争点入力待ちであることを表す。欠如時は `false` 扱い。次の `type:"input"` を主張本文として消費したら戻す一時的な内部状態。

## ポストモーテム

Markdownで次のセクションを持たせます。

- `設定された状況`
- `実際のタイムライン`
- `改善提案（総評）`
- `詳細評価`
- `要確認事項`（`/claim` で暫定採用した前提の真偽確認。該当なしなら「なし」）
- `参照すべき対応手順書`（理想タイムライン先頭行の `対応手順書` 欄から。`governing` を主手順書として明示。`重大度`・`エスカレーション先` は含めない。該当なしなら「なし」。各手順書は `ops/<name>.md` のパスで示す）
- `改善アクション`

### 対応手順書の表示

ポストモーテムの `参照すべき対応手順書` では、`ops/*.md` をそのままのパスで示します。
Markdown リンク（`[title](url)`）にはせず、素のパスを1行で示します（Slack は素の URL を
自動リンク化し、TTY でもそのままコピーしやすいため）。用途の1行補足はパスの後ろに添えて
よいです（例: `- ops/payment-failure.md — 用途`）。外部 Wiki に同期している場合は、その公開
URL を併記してかまいません。

## 事前生成データ (`timelines/SCN-xxx/`)

各シナリオの **バージョン1（＝理想状態）** の理想タイムライン・想定質問集・想定回答集を、事前生成済みデータとして `timelines/<シナリオID>/` に置きます。末尾の `-1` はバージョン番号です。

- `TIMELINE-1.tsv`: 理想タイムライン（バージョン1）。列構成は上記「タイムライン」と同じ。
- `QUESTIONS-1.tsv`: 理想タイムラインに対応する想定質問集。列構成は上記「想定質問集」と同じ。
- `ANSWERS-1.tsv`: 理想タイムラインに対応する想定回答集。列構成は上記「想定回答集」と同じ。

これらは演習開始時にユーザーが選んだモードに応じて使います（`.ai/skills/00-run-exercise/SKILL.md` 参照）。

- アドホック生成モード（自由度が高い・低速）: 理想タイムラインをその場で生成する。事前生成データは使わない。
- 事前生成再利用モード（自由度が低い・高速）: `TIMELINE-1.tsv` を理想タイムライン（`.ai/runs/<run-id>/TIMELINE-1.tsv`）として読み込む。`QUESTIONS-1.tsv` / `ANSWERS-1.tsv` は想定質問・回答を生成するときの **参考資料** として使う。

演習が進むと、対応者の行動により現在タイムラインは理想から離れます（状況が悪化しうる）。`TIMELINE-1.tsv` から `TIMELINE-2.tsv`, `TIMELINE-3.tsv` … と版が増え、想定回答集も版を重ねます（`.ai/agents/07`〜`09`）。事前生成データはバージョン1にのみ対応する参考資料であり、版が進んだ後は再生成された現在タイムラインを正とします。

事前生成3点が揃わないシナリオは、事前生成再利用モードでのみ選定対象外にします（`.ai/skills/01a-select-scenario/SKILL.md`）。

## シナリオ一覧 (`SCENARIO-LIST.tsv`)

シナリオを選びやすいよう、リポジトリルートに `SCENARIO-LIST.tsv` を事前生成します。

```tsv
ID	初動対応部署	最初の開示可能イベント	受動対応部署
```

表示用列（参加者へ提示してよい）は `ID` / `初動対応部署` / `最初の開示可能イベント` の3列で、`受動対応部署` は**末尾**に置く GM 内部専用の非表示列です（表示用3列の位置を変えないため末尾に追加します）。

- `ID`: `SCENARIO.tsv` のシナリオID。**（表示用列）**
- `初動対応部署`: 当該シナリオの**最初の可視イベントを初動で受け取る/対応する部署**。`;` 区切りで書く（通常は1つ。初動が真に複数部署で共同のときだけ複数）。判定できないときは `不明`、`最初の開示可能イベント` が `事前生成なし` / `開示可能情報なし` のときはそれに合わせる。後続で関与する部署は載せない（規模・原因のヒントになり公開できなくなるため）。システム名・ベンダー名（`frontend` / `paymentservice` / `cartservice` / `checkoutservice` / `valkey` / `kafka` / `postgres` 等）は部署ではないので入れない。表記揺れは正規形に正規化する。**（表示用列）**
- `最初の開示可能イベント`: 当該シナリオの `timelines/<ID>/TIMELINE-1.tsv` で最初に開示できる観測情報（`開示可能情報` に実際の観測情報が現れる最初の行）の要約。**（表示用列）**
- `受動対応部署`: 当該シナリオで、`初動対応部署`（列）以外に、NPC からの対応要請を受けて能動的に対応する部署（個別訓練の受動対応者になりうる部署）。`;` 区切り。該当が無ければ空。判定基準は `.ai/agents/90-build-scenario-list.md` 手順3.5。**GM 内部専用の非表示列**で、`01b` は表示せず、個別訓練のおすすめ絞り込みだけに使う（後続関与部署は規模・原因のヒントになるため参加者へは出さない）。

`.ai/agents/90-build-scenario-list.md` で（再）生成し、シナリオや事前生成タイムラインを追加・変更したときに更新します。表示は `.ai/skills/01b-list-scenarios/SKILL.md` が担います。

**開示の範囲**: 参加者へ提示してよいのは**表示用列**（`ID` / `初動対応部署` / `最初の開示可能イベント`）だけです（各行は `開示可能情報` の要約と、その初動対応部署のみ）。`初動対応部署` 列に後続で関与する部署を含めず初動だけに限るのは開示安全のためです（初動部署は最初の可視イベントから既に示唆されるためネタバレにならない一方、後続で登場する部署まで並べると事案の規模・原因のヒントになる）。`シナリオ` 概要（原因のネタバレ）や `開示不能情報` は含めません。表示用列以外の列を追加する場合は**GM内部専用**とし、`01b` は表示せず参加者へ出しません（`SCENARIO-LIST.tsv` をファイルごと参加者へ共有せず、参加者へ出すのは `01b` の整形済み表示用列だけにします）。

## シナリオ追加（canonical build）

新しいシナリオは、1つの入力（`ops/<番号>.md` 障害対応手順書 / `INCIDENTS.tsv` の1行）から `.ai/skills/92-build-scenario/SKILL.md` で1件ずつ追加します。92 は次の canonical 成果物を生成・更新します。

- `SCENARIO.tsv` に1行追記し、`scenarios/<新ID>` 分割ファイルを書き出す。
- `timelines/<新ID>/` に事前生成3点（`TIMELINE-1.tsv` / `QUESTIONS-1.tsv` / `ANSWERS-1.tsv`）を作る。列構成は上記「事前生成データ」と同じ。
- `.ai/agents/90-build-scenario-list.md` を呼んで `SCENARIO-LIST.tsv` を全件再生成し、索引へ反映する。

`.ai/runs/<run-id>/` のような演習作業ディレクトリは使いません（92 は演習中ではなく canonical 正本を直接更新するフロー外の保守ツール）。レビュー時に版を重ねる `REVIEWED-ANSWERS-<N>.tsv` も作らず、`timelines/<ID>/` は3点構成を保ちます（開示レビューは `ANSWERS-1.tsv` を直接修正）。

### `元リスク事象ID` の値規約

`SCENARIO.tsv` の `元リスク事象ID` は入力種別に応じて次の規約で書きます（`;` 区切りで複数可）。

- `INCIDENTS.tsv:N`: `INCIDENTS.tsv` の行番号（ヘッダ込み1始まり）。例: `INCIDENTS.tsv:2`。
- `OPS-CASE-NN`: 障害事例型の対応手順書（`ops/`）由来。
- `OPS-FREQ-NNN`: 恒常運用型の手順書（`ops/`）由来。

根拠が見つからない項目は推測で埋めず空欄にします（`docs/SPEC.md` フォーマット節）。

### 先頭データ行の重大度・エスカレーション注記

各 `timelines/<ID>/TIMELINE-1.tsv` の最初のデータ行（隠れた発端＝状況変化の行）の `開示不能情報`（列4）末尾には、GM 内部メモとして次を注記します（参加者には出さない列）。

- `根拠:` 着想・タイムラインの根拠にした `scenarios/` / `ops/` / `ref/` パス。
- `対応手順書: ...（governing: <主たる手順書>）` 当該シナリオを統べる対応手順書。
- `重大度: <SEV1 / SEV2 / SEV3>（事由: ...）` 判定根拠は `ops/incident-handling-manual.md`（顧客影響の範囲・継続時間・データ毀損の有無で決める）。
- `エスカレーション先: ...` 招集・通知する役割（例: SEV1 はインシデントコマンダーを招集し経営層へ第一報、SEV2 は影響サービスの開発オンコール、SEV3 は不要）。

この注記は列4（非開示）にのみ書き、参加者向け面（列2の能動通知本文・列3の `開示可能情報`・`SCENARIO-LIST.tsv`）には出しません。
