# IPCプロトコル

Unix Domain Socket 上で JSONL を使います。1行に1つの完全なJSONオブジェクトを書きます。各接続は1回の req/resp（送信1件、または受信1件）で完結し、socket を開きっぱなしにしません。会話用プロセス `ttx-human` は接続が閉じても終了せず、未回収の参加者入力をメモリ上のキューに貯めて次の接続を待ちます。

IPCメッセージは `type` と `text`、および省略可能な `thinking`（思考中表示の制御。後述）を持ちます。人間に表示される `text` は必ず日本語で書きます。

## Coding Agent から会話用プロセスへ

```json
{"type":"notification","text":"PagerDutyで注文APIの5xx増加アラートが発火しました。"}
```

許可する `type` は次の通りです。

- `answer`
- `notification`
- `question`
- `postmortem`
- `error`

`question` は、訓練モード（全体/個別）の選択やシナリオ選択など、**参加者へ回答を求める問い**に使います。`notification`（一方向の能動通知）と違い、送った後に `ttx-ai-recv` で参加者の回答を受け取る前提のメッセージです。回答は会話用プロセスから `type:"input"` として返るので、Coding Agent はその本文を質問・行動ではなく**設定回答**として解釈します。送る情報は他の type と同じく開示可能な情報だけに限ります。

会話用プロセスは、Coding Agentから受け取ったメッセージをすべて表示します。そのため、Coding Agentは参加者に見せてよい情報だけをIPCへ送らなければなりません。デバッグイベント、隠し状態、未来のタイムライン、開示レビュー記録、その他の内部情報はIPCへ送らず、内部ファイルに書きます。

#### `thinking`（思考中表示の制御、省略可）

メッセージに省略可能な `thinking`（真偽値）を付けられます。これは表示後の思考中インジケータ（応答待ちスピナー）の状態を表します。

```json
{"type":"notification","text":"演習を開始します。最初のメッセージまで1〜2分ほどお待ちください。","thinking":true}
```

- 既定（`thinking` なし＝false）: 会話用プロセスは GM メッセージを表示すると思考中表示を解除します（最初の GM メッセージで自動的に止まる）。
- `thinking:true`: 表示後も思考中表示を点けたままにします。演習開始直後の準備（理想タイムライン生成〜開示レビュー）に2〜3分かかる間、参加者へ「準備中である」ことを伝えるために使います。**次のフラグなし（thinking:false）の GM メッセージの表示で解除される**ので、最初のイベント開示（`06-disclose-first-event` の `notification`）は通常どおりフラグなしで送れば自動的にスピナーが止まります。
- 会話用プロセス起動直後は思考中ではありません（スピナーは出ません）。`thinking:true` のメッセージが届いて初めて点きます。

## 会話用プロセスからCoding Agentへ

```json
{"type":"input","text":"直近のリリースはありますか？"}
```

許可する `type` は次の通りです。

- `input`
- `control`

### `input` の運用

会話用プロセスは、`/help`・`/giveup`・`/claim`・`/abort` 以外の人間入力をすべて `type:"input"` として送ります。Coding Agentは `input` の本文を、スラッシュの有無で決めず内容から「質問」「行動」「その両方」に分類します（`.ai/agents/07-handle-question-or-action.md`）。

### `control` の運用

`control` は演習の進行を制御する操作です。規定するのは次の3つで、これ以外の `control` 操作は規定しません。

```json
{"type":"control","text":"/giveup"}
{"type":"control","text":"/abort"}
{"type":"control","text":"/claim 部長判断は不要です"}
```

- `/giveup`: 演習の終了宣言。Coding Agentは、ゲーム内イベントを捏造せず、タイムラインを進めず、能動通知も送らず、`.ai/runs/<run-id>/timeline_cursor.json` のカーソル状態を `finished` にしてポストモーテム生成へ進みます。`text` に続く文言（例: `/giveup もう無理です`）は内部ログに記録してよいですが、開示してはいけません。
- `/abort`: ポストモーテムを作らない中断。Coding Agentは、ゲーム内イベントを捏造せず、タイムラインを進めず、能動通知も送らず、カーソル状態を `aborted` にします。`/giveup` と異なりポストモーテムは生成せず、短い中断通知だけを送って終了します（`.ai/skills/00-run-exercise/SKILL.md` のステップ13）。`text` に続く文言は内部ログに記録してよいですが、開示してはいけません。
- `/claim <主張>`: GM の前提への異議申し立て。Coding Agent は主張を暫定的に真として受け入れ（`CLAIMS.tsv` に記録）、直前にその前提で保留した行動があれば新しい前提で再評価して進めます。受領は中立な `answer` で返し、シナリオが実際にその前提を要したか否かは開示しません（真偽はポストモーテムの「要確認事項」で人間に確認させます）。本文なしの `/claim` を受けたら、何を争点とするか `answer` で尋ね、次の `type:"input"` を主張本文として扱います（GM 側の `awaiting_claim` 状態）。詳細は `.ai/agents/07-handle-question-or-action.md`。

### 受信要求（recv）

Coding Agent は次の参加者入力を受け取るために、`type:"recv"` の制御メッセージを送ります。これは人間には表示されず、`public_log.jsonl` にも記録しません。`text:"wait"` のとき会話用プロセスは入力が来るまでブロックして1件返し、`text` が空のときは滞留が無ければ何も返さず接続を閉じます。応答の本文は上記の `input` または `control` です。

#### アイドルタイムアウト（recv の打ち切り）

会話の最後のアクティビティ（参加者入力または GM 送信）から一定時間（会話用プロセスの `--recv-timeout`、既定 30 分）参加者入力が無いと、`text:"wait"` の recv は応答 `type:"timeout"` を返して打ち切ります。この `timeout` 応答は server→GM 方向の recv 応答専用で、人間には表示されず送信もできません。締切は最後のアクティビティ基準で測るため、GM が recv を何度再実行しても総アイドル時間で打ち切られます（ホスト側のツールタイムアウトで recv を繰り返す際のトークン浪費を防ぐ）。

GM 側は `ttx-ai-recv` の終了コード `5` でこれを受け取り、**`/abort` 相当（ポストモーテムを作らない中断）**として終了します（`.ai/skills/00-run-exercise/SKILL.md` のステップ13中断分岐）。`--recv-timeout 0` で無期限（タイムアウト無し）にできます。

## GM 側ツール

Coding Agent は socket を自前実装で開かず、専用 CLI を使います（`nc` や Python 等を毎回書かないこと）。`--socket` は省略可で、`TTX_SOCKET` か既定パス（`$XDG_RUNTIME_DIR/ttx.sock`、無ければ `$TMPDIR/ttx-<uid>.sock`）を 3 ツールで共有します。別パスにしたいときだけ全ツールへ同じ `--socket` か `TTX_SOCKET` を指定します。既定パスは uid と環境変数から算出するため、3 ツールは同一ユーザー・同一環境で動かしてください（別ユーザーや sudo を跨ぐと別パスになり疎通しません。その場合は `--socket` か `TTX_SOCKET` で明示的に揃える）。

- 送信: `ttx-ai-send [--socket <path>] --type <answer|notification|question|postmortem|error> --text '…'`（長文は `--text-file <path>` か stdin）。送信できる `type` は上記5種だけで、それ以外は拒否されます（終了コード3）。`--thinking` を付けると表示後も思考中表示を点けたままにします（演習開始通知など。`thinking:true` を送る）。
  - 改行: `--text` は `\n` 等の Go 形式エスケープを実改行へ展開するので、選択肢列挙などの複数行は `--text '1. …\n2. …'` と1行で書けます（シェルのシングルクォートでは `\n` が解釈されないため、ツール側で展開します）。リテラルなバックスラッシュを保ちたい長文は `--text-file`・stdin を使ってください（どちらも生バイトのまま送ります）。
- 受信: `ttx-ai-recv [--socket <path>] [--wait]`（既定は `--wait`＝次入力までブロック）。受け取った1行（`{"type":"input"|"control",…}`）を stdout に出します。滞留が無いとき即終了したい場合は `--no-wait`（空のまま終了コード4）。アイドルタイムアウトで打ち切られた場合は **終了コード5**（stdout は空。`/abort` 相当として扱う。上記「アイドルタイムアウト」を参照）。

各コマンドは1接続につき送信または受信を1件だけ行って終了します。socket への接続失敗（終了コード2）は IPC 障害として扱います。終了コードは `0`=取得 / `2`=接続・送受信失敗 / `4`=滞留無し / `5`=待機タイムアウト（abort 相当）です。演習のライブ進行中に IPC 障害（終了コード2）が起きたら、会話用プロセス（`ttx-human` またはゲートウェイ）が失われたとみなし、リトライせず演習を中断します（演習側の具体的な扱いは `.ai/skills/00-run-exercise/SKILL.md` の「IPC 障害時の扱い」に従う）。

## 会話用プロセスのローカルコマンド

`/help`（別名 `?`）は会話用プロセスがローカルで処理し、利用可能なコマンド一覧を対応者へ表示します。IPCへは送られず、Coding Agentは受け取りません。表示内容は `ttxserver` パッケージの `Commands` を定義元とし、会話UIの `?` 表示（関連 issue #3）もこれを再利用します。

## フィールド

- `type`: メッセージ種別（必須）
- `text`: 日本語の本文（必須）
- `thinking`: 表示後の思考中表示の状態（省略可。既定 false。上記「`thinking`」を参照）

## 安全ルール

- Coding Agentは演習中、人間が見る端末へ直接書いてはいけません。
- IPCメッセージに、隠れた原因、未来イベント、シナリオID、想定質問、想定回答、レビュー記録、agentの思考過程を含めてはいけません。
- 内部情報は会話用プロセスへ送らず、内部ログまたは中間ファイルに書きます。
