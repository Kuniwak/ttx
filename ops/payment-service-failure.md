# 対応手順書: 決済サービス障害（checkout 決済段の失敗）

`payment` サービスがカード課金に失敗し、`checkout`（注文確定）の決済段でエラーが増えるインシデントの対応手順です。クリティカルパス上の障害で、顧客が注文を完了できなくなります。

関連: `ref/otel-demo/architecture.md`（チェックアウトのフロー）、`ref/otel-demo/failure-scenarios.md`（`paymentServiceFailure`）、`ops/incident-handling-manual.md`（体制・Severity・エスカレーション）。

## 基本情報

| 項目 | 内容 |
| --- | --- |
| 想定 Severity | SEV1（チェックアウトの決済段が広範に失敗し、注文を完了できない） |
| 主担当 | SRE（一次対応）/ 開発（payment オーナー） |
| 連携 | インシデントコマンダー / カスタマーサポート / 広報 |

## 検知導線

- 監視アラート: `checkout` のエラー率急増（Prometheus/Grafana）→ オンコール（SRE）。
- 業務側起点: 「決済できない／注文が完了しない」という顧客問い合わせがカスタマーサポートに入る。

## 対応の流れ

| 着手タイミング | 役割 | 作業 | チェック項目 |
| --- | --- | --- | --- |
| 検知直後 | SRE | アラートを確認し暫定で障害認定、Severity を置く | エラー率の対象サービス・メトリクス |
| 認定後 | SRE / インシデントコマンダー | IC・記録担当・次回更新時刻を宣言 | 指揮系統の一本化 |
| 調査 | SRE | 失敗リクエストのトレースとサービス別エラー率で切り分け | どの境界（checkout→payment）で失敗しているか |
| 調査 | SRE / 開発 | 直近の変更（デプロイ・設定・フラグ）の履歴を確認 | 直近の payment 関連変更の有無 |
| 緩和 | SRE / 開発 | 直近変更の切り戻し（フラグ無効化/ロールバック）を実施 | 実行前後の指標、中止条件 |
| 復旧確認 | SRE | エラー率・成功率の回復と安定を確認 | 基準内で一定時間安定 |
| 周知 | 広報 / カスタマーサポート | 復旧の確定事実のみを社内外へ周知 | 推測・内部実装を出さない |
| 影響整理 | SRE / カスタマーサポート | 影響時間帯の失敗注文・顧客範囲を特定、救済要否を判断 | 二重課金・未確定注文の有無 |
| 収束 | SRE | 収束宣言、改善チケットと Runbook 改訂を登録 | オーナー・期限・完了条件 |

## 緩和の原則

原因究明より先に顧客影響を止める（mitigation first）。決済段の失敗が直近変更に起因する場合は、恒久修正の前にまず変更を切り戻す。`accounting` / `fraud-detection` は Kafka 経由の非同期処理であり、チェックアウト応答のクリティカルパス外（遅延は後追いで確認）。

## 顧客向けコミュニケーション

確定した事実と回避策のみを伝える。内部実装の詳細やフラグ名、未確定の原因は開示しない。
